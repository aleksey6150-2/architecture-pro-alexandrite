# Архитектурное решение по логированию

## 1) Контекст и цели

Сейчас разбор инцидентов происходит “со слов клиента”. При росте нагрузки и появлении B2B API это приводит к:
- долгим расследованиям (ищем вручную по разрозненным логам/БД),
- невозможности доказуемо ответить партнёрам “что произошло с заказом”,
- высокой нагрузке на поддержку и разработчиков.

Цель: внедрить **централизованное структурированное логирование** со сквозными идентификаторами (`trace_id`, `order_id`, `message_id`, `client_id`), чтобы по одному запросу в логах можно было восстановить историю заказа/ошибки.

---

## 2) Мотивация

### 2.1 Что даст компании
- Быстрый ответ на вопросы:
    - “где сейчас заказ?”
    - “почему заказ не появился в CRM/MES?”
    - “почему MES грузится долго?”
- Сокращение времени расследования инцидентов и количества “необъяснимых” случаев.
- Повышение прозрачности для B2B (можно оперировать фактом: request_id/trace_id и этап обработки).
- Возможность строить алёрты и отчёты по ошибкам и аномалиям без участия разработчиков.

### 2.2 Метрики (технические/бизнес), на которые повлияет логирование
1) **MTTR** (mean time to recovery) — снизится за счёт быстрого поиска по `order_id/trace_id/message_id`.
2) **Количество эскалаций в разработку** — снизится, часть кейсов будет разбирать поддержка по логам.
3) **Доля инцидентов без установленной причины** — снизится (видно исключения, цепочку вызовов, контекст).
4) **SLA по заказам / доля “пропавших заказов”** — улучшится за счёт обнаружения “дыр” и зависаний (через алёрты на DLQ/ошибки консьюмеров).
5) **Потери B2B контрактов** — снижаются, потому что появляется доказуемость и скорость реакции.

## 3) Какие системы покрыть сбором логов (и где заказ может “сломаться”)

### 3.1 Источники логов (по C4) — что обязательно собирать
**MVP (в первую очередь):**
1) **MES API (C#)** — критический контур (B2B + операторы + расчёт цены).
2) **CRM API (Spring Boot)** — подтверждения производства, изменения статусов, интеграция с RabbitMQ.
3) **RabbitMQ** (системные логи брокера + метрики; логи полезны для расследований, но основное — метрики)
4) **Shop API (Spring Boot)** — создание заказа, загрузка 3D, запись в Shop DB.

**Вторая очередь:**
5) **Ingress / LB** (nginx ingress controller) — access/error logs, чтобы видеть 4xx/5xx, source IP, всплески.
6) **PostgreSQL (Shop DB, MES DB)** — audit/slow query log (осторожно по объёму).
7) **S3 storage** — если доступно: access logs (операции put/get, ошибки).

### 3.2 Приоритезация: где настраиваем логирование и трейсинг сначала и почему
**Приоритет 1: MES API + CRM API + RabbitMQ контур**
- Потому что основные жалобы: “заказ не дошёл/завис” и “MES медленный”.
- Здесь чаще всего проявляются: дубли/потери сообщений, ошибки консьюмеров, долгие операции.

**Приоритет 2: Shop API**
- Потому что это вход B2C и загрузка файлов; важно для возникновения заказов и данных для расчёта.

**Приоритет 3: Ingress + DB slow logs**
- Для точечной оптимизации производительности и расследования сетевых/SQL проблем.

## 4) Какие логи собирать: список INFO-событий (минимальный “словарь”)

### 4.1 Общие требования к формату
- **Структурированные логи JSON** (одна запись = один JSON-объект).
- Обязательные поля в каждой записи:
    - `timestamp`, `level`, `service`, `env`, `version`
    - `trace_id`, `span_id` 
    - `request_id` (для HTTP)
    - `order_id` (если применимо)
    - `message_id` и `correlation_id` (для RabbitMQ событий)
    - `client_id` (для B2B)
    - `event` (тип события) и `result` (success/fail)
    - `duration_ms` (для измеримых операций)

### 4.2 Shop API (INFO)
1) `order_initiated` — создан черновик/корзина  
   Поля: `order_id`, `customer_id`(если есть), `source=B2C`
2) `file_upload_started` / `file_upload_finished`  
   Поля: `order_id`, `file_key`(или `file_hash`), `size_bytes`, `duration_ms`
3) `order_submitted`  
   Поля: `order_id`, `customer_id`, `items_count`, `has_file=true/false`
4) `db_write_order` (успешная запись заказа)  
   Поля: `order_id`, `duration_ms`
5) `message_published` (если Shop публикует события)  
   Поля: `message_id`, `exchange`, `routing_key`, `order_id`

### 4.3 CRM API (INFO)
1) `order_received_from_mq` (получили сообщение о новом заказе/статусе)  
   Поля: `message_id`, `order_id`, `status_to`, `redelivered`
2) `order_created` (создан заказ в CRM)  
   Поля: `order_id`, `source`, `duration_ms`
3) `manufacturing_approved`  
   Поля: `order_id`, `seller_id`, `duration_ms`
4) `status_changed` (универсальный лог)  
   Поля: `order_id`, `status_from`, `status_to`, `actor_type=seller/system`, `actor_id`
5) `message_published_to_mq` (публикация статуса в MQ)  
   Поля: `message_id`, `order_id`, `status_to`, `exchange`, `routing_key`

### 4.4 MES API (INFO)
1) `b2b_request_received` (если запрос от партнёра)  
   Поля: `client_id`, `request_id`, `route`, `order_id`(если есть)
2) `price_calc_started` / `price_calc_finished`  
   Поля: `order_id`, `file_key/file_hash`, `duration_ms`, `result`
3) `file_download_started` / `file_download_finished` (S3)  
   Поля: `order_id`, `file_key`, `size_bytes`, `duration_ms`
4) `order_assigned_to_operator` (claim/take)  
   Поля: `order_id`, `operator_id`, `result=success|conflict`, `duration_ms`
5) `status_changed`  
   Поля: `order_id`, `status_from`, `status_to`, `actor_type=operator/system`, `actor_id`
6) `order_list_requested` (для диагностики “первый экран тормозит”)  
   Поля: `operator_id`, `filters`(без PII), `duration_ms`, `rows_returned`

### 4.5 RabbitMQ (что логировать на стороне приложений)
На сам RabbitMQ мы полагаемся больше через метрики, но приложения должны логировать:
- `message_consumed`
- `message_acked`
- `message_nacked`
- `message_sent_to_dlq` (если логика DLQ на стороне приложения)

Поля: `queue`, `exchange`, `routing_key`, `message_id`, `correlation_id`, `order_id`, `attempt`, `redelivered`

## 5) Уровни логирования: какие используем и когда

- **INFO** — бизнес-значимые события и этапы обработки заказа (как выше).
- **WARN** — нестандартные, но обработанные ситуации:
    - повторная доставка `redelivered=true`,
    - попытка некорректного перехода статуса,
    - таймауты зависимостей с успешным ретраем,
    - rate-limit срабатывания для B2B.
- **ERROR** — ошибки, влияющие на корректность процесса:
    - не удалось обработать сообщение из MQ,
    - не удалось записать в БД,
    - ошибка скачивания/чтения файла из S3,
    - исключение в расчёте цены.
      В ERROR обязательно писать `exception.*` и `order_id/message_id`.

- **DEBUG/TRACE** — только в dev/release или временно на проде по фиче-флагу:
    - подробные payload’ы (без PII),
    - детали сериализации, low-level сетевые ошибки.  
      На проде включать точечно по `client_id` или `order_id` на короткий срок.

## 6) Предлагаемое решение (технологии и компоненты)

### 6.1 Архитектура сбора логов
Цель: централизованный pipeline “контейнер → сборщик → хранилище → поиск/дашборды → алёрты”.

**В Kubernetes:**
1) Все сервисы пишут логи в **stdout/stderr** в формате JSON.
2) DaemonSet-агент на нодах:
    - **Fluent Bit**
    - собирает контейнерные логи, добавляет метаданные k8s (namespace/pod/container)
3) Хранилище и поиск:
    - **OpenSearch** (или Elasticsearch) как движок хранения/поиска
    - **OpenSearch Dashboards** (или Kibana) как UI
4) (Опционально) архив:
    - S3-архивирование старых индексов (ILM/ISM политики)

**В облаке без k8s (как сейчас на EC2):**
- либо агенты Fluent Bit/Filebeat на инстансах, собирающие файлы логов,
- либо переход на containerized/managed logging.

### 6.2 Что нужно доработать в приложениях
- Включить JSON-логирование:
    - Spring Boot: Logback encoder (например, logstash-logback-encoder).
    - .NET: Serilog + JSON sink.
- Внедрить **корреляцию**:
    - `trace_id` из OpenTelemetry (если внедрён трейсинг),
    - `request_id` для каждого HTTP запроса,
    - `message_id` и `correlation_id` для RabbitMQ.
- Прокидывать `order_id` в MDC/лог-контекст при обработке запроса/сообщения.

### 6.3 Что отразить на C4-схеме (новые компоненты/связи)
Добавить (новые элементы выделить, например, красным/как “Observability”):
- **Log Agent (Fluent Bit)** на нодах: собирает stdout логов сервисов
- **Log Storage & Search (OpenSearch/Elasticsearch)**
- **Log UI (OpenSearch Dashboards/Kibana)**
- (Опционально) **Alerting** (встроенный в OpenSearch или внешний)

Связи:
- Shop API → Fluent Bit → OpenSearch
- CRM API → Fluent Bit → OpenSearch
- MES API → Fluent Bit → OpenSearch
- (Ingress controller → Fluent Bit → OpenSearch)
- Admin/Support → Log UI

## 7) Безопасность логов (PII, доступ, изоляция)

### 7.1 Работа с чувствительными данными
- Запрещаем писать в логи:
    - ФИО, телефон, email, адрес доставки, платежные данные,
    - полный 3D файл/контент (очевидно).
- Разрешаем писать:
    - `order_id`, `message_id`, `trace_id`, `client_id`,
    - технические коды ошибок, статусы, длительности.
- Маскирование/редакция:
    - если всё-таки нужно писать идентификаторы пользователя — только внутренний `customer_id` без персональных данных;
    - любые токены/ключи — маскировать (последние 4 символа).

### 7.2 Доступ к логам
- Логи доступны только внутри компании (VPN / private network).
- RBAC роли:
    - Support: чтение логов, поиск по `order_id`, без доступа к raw payload
    - Engineering/DevOps: расширенный доступ
- Аудит: логировать обращения к UI/экспорт логов.

## 8) Политика хранения (retention), индексы и объём

### 8.1 Индексация
Рекомендуется отдельные индексы по сервисам/окружениям:
- `logs-shop-api-prod-YYYY.MM.DD`
- `logs-crm-api-prod-YYYY.MM.DD`
- `logs-mes-api-prod-YYYY.MM.DD`
- `logs-ingress-prod-YYYY.MM.DD`

Причины:
- проще управлять retention и доступами,
- проще искать без “шума”.

### 8.2 Срок хранения (стартовые значения)
- PROD:
    - INFO/WARN/ERROR: 14–30 дней в “горячем” поиске
    - Архив (S3): 90–180 дней (если требуется для разборов/контрактов)
- DEV/RELEASE: 7–14 дней

### 8.3 Контроль размера
- Ввести лимиты на DEBUG
- Сэмплинг для шумных INFO-событий (например, access logs) — по необходимости
- Ротация индексов (ILM/ISM)

## 9) Превращение “сбора логов” в “анализ логов”: алёрты, аномалии, расследования

### 9.1 Алертинг (минимум)
Нужно настроить алёрты по логам (в дополнение к метрикам):
- всплеск `level=ERROR` в сервисе MES API за 5 минут
- появление ошибок обработки RabbitMQ сообщений (`message_nacked`, `consume_failed`)
- “price_calc_failed” > N за интервал
- рост 5xx в ingress logs

Каналы: чат/почта + автосоздание тикета.

### 9.2 Поиск аномалий
Примеры правил (простые, пороговые):
- `order_submitted` вырос в 100 раз за минуту → подозрение на DDoS/ботов
- `b2b_request_received` по одному `client_id` резко вырос → ввод квот/блокировка
- резкий рост `redelivered=true` → проблемы консьюмеров/ack

## 10) Дополнительное: критерии выбора технологии (ELK vs OpenSearch vs Splunk)

| Критерий                     | ELK (Elastic)                         | OpenSearch                     | Splunk                        |
|------------------------------|---------------------------------------|--------------------------------|-------------------------------|
| Лицензия/стоимость           | Elastic License (ограничения)         | Apache 2.0 (открытая)          | Проприетарная, дорогая        |
| Стоимость владения (TCO)     | Средняя/высокая (зависит от лицензий) | Ниже при self-hosted           | Высокая                       |
| Простота эксплуатации        | Средняя                               | Средняя                        | Выше “из коробки”, но дорогая |
| Масштабирование и перформанс | Высокие возможности                   | Высокие возможности            | Высокие                       |
| Эко-система и интеграции     | Очень широкая                         | Широкая (совместима во многом) | Богатая, enterprise           |
| Alerting/ML аномалии         | Есть (часто платно)                   | Есть (часть free)              | Сильные возможности           |
| Vendor lock-in               | Средний                               | Низкий                         | Высокий                       |
| Подходит команде 1 DevOps    | Можно, но нужна дисциплина            | Обычно чуть проще по лицензии  | Может быть проще, но дорого   |

**Рекомендация для “Александрита” на MVP:** OpenSearch + Fluent Bit  
Причины:
- открытая лицензия,
- достаточно возможностей для поиска/алёртов,
- относительно подъёмно для небольшой команды.

## 11) План внедрения (по шагам)

1) Ввести стандарт JSON-логов и обязательных полей (service/env/trace_id/order_id/message_id/client_id).
2) Настроить сбор stdout логов (Fluent Bit DaemonSet) в k8s.
3) Развернуть OpenSearch + Dashboards (или managed аналог).
4) Настроить индексы/retention и RBAC.
5) Добавить алёрты по ERROR и по ключевым паттернам (MQ failures, price_calc_failed).
6) Обучить поддержку: чек-листы поиска “по order_id”, “по message_id”, “по client_id”.
