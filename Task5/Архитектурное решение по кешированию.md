# Архитектурное решение по кешированию

## 1) Контекст и проблема

По описанию и C4-диаграмме основные боли сейчас в MES:

- **Операторам медленно открывается первая страница MES** (список заказов “в работе” по статусам, с фильтром/пагинацией).
- **Новые клиенты (в т.ч. B2B через API) недовольны сроками выполнения заказа**; один из факторов — высокая нагрузка на MES контур и длинные операции.
- Текущая инфраструктура: **по 1 инстансу** каждого приложения + БД без read-replica → любое “тяжёлое чтение” бьёт по записи и общей отзывчивости.

Кеширование здесь нужно прежде всего для снижения нагрузки на **MES DB** и ускорения **частых чтений** (дашборд/списки), не ухудшая корректность “самых новых заказов”.

---

## 2) Мотивация

### 2.1 Зачем внедрять кеширование
Кеширование предлагается, чтобы:

1) **Ускорить MES dashboard** (первую страницу) до предсказуемых задержек (например, p95 < 300–500 мс на backend).
2) **Снизить нагрузку на MES DB**, уменьшить конкуренцию чтения/записи (особенно при росте заказов).
3) **Стабилизировать систему при росте B2B нагрузки**: чтения/листинги не должны “съедать” ресурсы и ухудшать обработку статусов/расчётов.
4) Дать основу для дальнейшей оптимизации (keyset pagination, read-модель), не ломая текущую доменную модель.

### 2.2 Какие элементы системы кешируем
В рамках данного задания имеет смысл кешировать именно **MES read-сценарии**, потому что жалобы операторов напрямую про скорость UI и список заказов:

- список “новые заказы по статусу” (и/или “по статусам”)
- агрегаты по статусам (кол-во в каждом статусе)
- карточку заказа (часто открывают после списка) — опционально, вторым этапом

Дополнительно (вне MES): в интернет-магазине можно кешировать каталог/справочники, но это не решит текущую боль MES.

## 3) Предлагаемое решение (основное)

### 3.1 Тип кеширования: серверное (Redis) + минимально клиентское
**Выбор:** серверное кеширование в MES API с внешним кешем (Redis).

**Почему серверное:**
- Операторов много, а данные общие → клиентский кеш даёт слабый эффект и не решает нагрузку на БД.
- Нужна централизованная стратегия инвалидации при смене статусов/взятии заказа.

**Клиентское кеширование** можно добавить параллельно только для статики/справочников UI, но ключевой эффект даст Redis.

### 3.2 Паттерны кеширования: Cache-Aside + “Update-on-write” для индексных структур
Для MES списка заказов предлагается комбинировать:

- **Cache-Aside** для выдачи списка/карточек:
    - API читает из Redis; при miss — читает из DB и кладёт в кеш с TTL.
- **Обновление/инвалидация при записи** (программная инвалидация) для поддержания “почти свежих” списков:
    - при смене статуса/назначении заказа оператору MES API обновляет кеш-структуры (или инвалидирует ключи).

Почему не Write-Through / Refresh-Ahead “в чистом виде”:
- **Write-Through** хорошо для простого key-value, но список заказов — это “индекс” (топ-N по статусу, сортировка по времени), его проще поддерживать отдельной структурой в Redis и обновлять событием.
- **Refresh-Ahead** требует фона/воркеров и правильного предсказания горячих ключей; у нас “самое новое” и частые изменения — проще и надёжнее обновлять при статусных событиях.

### 3.3 Структура кеша (ключи и сущности)

**Вариант реализации на Redis (рекомендуемый для MVP):**

1) **Sorted Set по статусу для самых новых заказов**  
   Ключ: `mes:orders:by_status:{STATUS}` (Redis ZSET)
- member: `order_id`
- score: `created_at_epoch` или `updated_at_epoch` (лучше `updated_at`, если “новизна” = последние изменения)

Так можно быстро отдавать “самые новые”:

- `ZREVRANGE mes:orders:by_status:MANUFACTURING_APPROVED 0 49`

2) **Кеш деталей заказа**  
   Ключ: `mes:order:{order_id}` (Redis HASH/STRING JSON)  
   TTL: 5–30 минут (настраивается)

3) **Агрегаты по статусам (для дашборда)**  
   Ключ: `mes:orders:count_by_status` (HASH: status → count)  
   или отдельные ключи `mes:orders:count:{STATUS}`

> Примечание: ZSET по статусу может стать большим. Для интерфейса операторов часто достаточно хранить **последние N (например 5–50 тыс.)**: при обновлениях выполнять `ZREMRANGEBYRANK` для обрезки хвоста.

## 4) Стратегия инвалидации кеша

Нужна комбинация стратегий, потому что данные меняются часто, а бизнесу важна “почти реальная” свежесть.

### 4.1 Предлагаемая стратегия (рекомендуемая)
1) **Программная инвалидация/обновление при записи** (ключевая):
- при любом изменении статуса в MES:
    - обновить ZSET-индексы (переместить `order_id` между статусами)
    - инвалидировать/обновить `mes:order:{id}`
    - обновить счетчики по статусам

2) **TTL как “страховка”**:
- детали заказа: TTL 5–30 минут (на случай рассинхрона/непредвиденных путей изменения)
- индекс по статусу: TTL можно не ставить (если поддерживаем on-write), либо ставить короткий TTL и периодически пересобирать (сложнее)

3) **Инвалидация по событиям** (если статусы приходят также извне, например из CRM через MQ):
- консьюмер событий в MES API при получении `OrderStatusChanged` должен выполнять те же операции обновления кеша (ZREM/ZADD + обновление деталей)

### 4.2 Почему не только временная (TTL) инвалидация
Только TTL приведёт к:
- устаревшим спискам (“операторам важно видеть самые новые”)
- скачкам нагрузки при истечении TTL (cache stampede)
- сложным багам “заказ уже взяли, но он ещё виден как свободный”

TTL оставляем как fallback, а основная консистентность — через on-write обновления.

## 5) Дополнительное задание: два варианта решения и сравнение

Ниже — два допустимых архитектурных решения. Оба решают проблему, но с разной сложностью и гарантиями.

### Решение 1 (рекомендуемое): Redis cache + индексы списков (описано выше)
**Описание:** Redis как серверный кеш; ZSET по статусам + кеш деталей; обновление индексов при смене статуса.

**Плюсы:**
- Быстрый эффект по latency для дашборда.
- Снимает нагрузку с MES DB.
- Хорошо подходит под “покажи самых новых”.
- Гибко масштабируется (Redis можно вынести в managed).

**Минусы:**
- Нужно аккуратно реализовать инвалидацию/обновления.
- Риск рассинхрона при ошибках в обработке событий (смягчается TTL + мониторинг).
- Доп. компонент инфраструктуры (Redis).

---

### Решение 2: Read-model (проекция) в PostgreSQL (денормализация) + оптимизация запросов
**Описание:** Создать отдельную таблицу/проекцию `order_status_projection` (order_id, status, updated_at, operator_id, …) и держать её актуальной при изменениях статуса. Для дашборда читать только проекцию с правильными индексами и keyset pagination.

**Плюсы:**
- Меньше внешних компонентов (без Redis).
- Сильнее консистентность (в рамках одной БД/транзакции).
- Проще резервное копирование/восстановление.

**Минусы:**
- Нагрузка остаётся на DB (хоть и меньше, чем на “боевых” таблицах).
- При резком росте чтения всё равно может потребоваться read replica.
- Дашборд “по статусам” может потребовать агрегаций, которые снова станут тяжёлыми без кеша.

---

### Сравнительная таблица

| Критерий                           | Решение 1: Redis кеш + ZSET      | Решение 2: Read-model в Postgres       |
|------------------------------------|----------------------------------|----------------------------------------|
| Время до эффекта                   | Быстро (1–2 спринта MVP)         | Среднее (нужно моделирование проекции) |
| Скорость дашборда при росте данных | Очень высокая (O(log N) по ZSET) | Высокая, но зависит от индексов/IO     |
| Нагрузка на MES DB                 | Сильно снижается                 | Снижается частично                     |
| Консистентность                    | Eventual + on-write обновления   | Обычно сильнее (если в транзакции)     |
| Операционная сложность             | + Redis как компонент            | Без Redis, но больше SQL/схемы         |
| Риск рассинхрона                   | Есть (лечится TTL/алёртами)      | Меньше                                 |

### Заключение
Для “Александрита” в условиях срочной боли MES рекомендую **Решение 1 (Redis)** как MVP, параллельно запланировав **оптимизацию запросов/индексов** (keyset pagination) и/или постепенный переход к read-model для стабильности на большом масштабе.

## 6) План внедрения (высокоуровневый)

1) Выбрать и развернуть Redis (лучше managed) для prod/release.
2) Реализовать в MES API:
    - чтение списка через ZSET + кеш деталей
    - обновление кеша при смене статуса (и при событиях из MQ)
3) Ввести метрики:
    - cache hit ratio по спискам/деталям
    - latency endpoint’ов дашборда
4) Настроить алёрты:
    - hit ratio резко упал
    - рассинхрон: заказ в DB со статусом X не попадает в индекс X (периодический аудит/джоб)
5) (Следующий шаг) Оптимизация DB: индексы + keyset pagination на случай cache miss.
