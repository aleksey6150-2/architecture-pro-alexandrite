1) Идентификация проблемных мест (существующие и потенциальные)

1.1. Надёжность заказов и статусов (ключевая бизнес-боль)
P1. Потеря/задержка событий о заказах и статусах между системами
- Симптомы: клиенты и API-партнёры «не получили заказ», заказы «висят месяцами».
- Вероятные причины:
  - Нет гарантированной доставки/обработки событий (at-least-once/ exactly-once).
  - Отсутствие идемпотентности обработчиков: дубликаты → ошибки/откаты; или наоборот, “drop” при повторе.
  - Нет outbox/inbox-паттернов: запись в БД и публикация в RabbitMQ могут расходиться.
  - Нет DLQ/parking lot очередей и управляемых ретраев → «ядовитые» сообщения стопорят поток.
  - Нет наблюдаемости по лагу очередей/ошибкам консьюмеров → проблемы накапливаются незаметно.
  - Ручные релизы и один инстанс консьюмера → простои при деплое → лаг → лавина.

P2. Несогласованность статусов между Shop/CRM/MES
- Статусы меняются в разных системах;
- Нет “источника истины” по жизненному циклу заказа

1.2. Производительность и высокая нагрузка
P3. Долгий расчёт стоимости (2–30 мин) + внешний API
- Расчёт тяжёлый и, судя по симптомам, влияет на общее качество:
  - Если расчёт выполняется синхронно в MES API, он держит ресурсы, потоки, соединения с БД/хранилищем.
  - Открытие API партнёрам кратно увеличило поток расчётов и/или заказов → эффект “очереди” и деградация всего MES.
- Нет явной защиты от всплесков:
  - нет rate limiting/quotas на внешнем API,
  - нет backpressure и приоритизации B2C vs B2B,
  - нет отдельного пула воркеров под CPU-bound/IO-bound задачи.

P4. Тормозит первая страница MES (дашборд заказов по статусам)
- Фильтр и пагинация “не помогли” — признак:
  - запросы всё равно тяжёлые
  - отсутствуют нужные индексы (например, по (status, created_at), (status, updated_at)),
  - данные “по статусам” считаются on-the-fly вместо предагрегации/кеша/материализованного представления.
- Бизнес-требование “самые новые заказы важнее” намекает на необходимость:
  - keyset pagination (seek),
  - быстрый доступ к “top-N newest by status”,
  - отдельной read-модели.

P5. SPOF по приложениям и БД
- По 1 инстансу каждого приложения → любая проблема/деплой = простой.
- БД без read-replica → рост чтения (дашборды, списки) конкурирует с записью (статусы/заказы).

1.3. Наблюдаемость и управление инцидентами
P6. Отсутствие мониторинга/алёртинга уровня продукта и интеграции
- Нет сигналов:
  - lag RabbitMQ по ключевым очередям,
  - количество ошибок консьюмеров, ретраи, DLQ,
  - длительность расчёта цены и её очередь,
  - время прохождения заказа по статусам (lead time),
  - SLO по “заказ создан и дошёл до производства”.

P7. Нет распределённой трассировки и корреляции
- Без trace/correlation-id невозможно быстро доказать, где “пропал” заказ: Shop → CRM → MQ → MES.

1.4. Процессы поставки (ускоряют накопление проблем)
P8. Ручное E2E и ручные релизы → длинный lead time изменений
- QA вручную, релизы задерживаются на недели/месяцы.
- В условиях роста нагрузки и инцидентов это означает “не успеваем чинить”.

1.5. API для партнёров (B2B)
P9. Внешний API напрямую на MES API без “периметра”
- Риски:
  - отсутствие rate limiting и контроля клиентов,
  - отсутствие версии/контрактов/политик ретраев,
  - отсутствие изоляции от внутренних сбоев (партнёры “роняют” MES, MES “роняет” партнёров).

2) Инициативы (что нужно сделать)
Ниже — список инициатив, от архитектурных эпиков до точечных задач. Формулировки намеренно “проверяемые” (можно принять/сдать).

2.1. Наблюдаемость (мониторинг, логи, трассировка) — фундамент
I1. Ввести сквозной correlation-id для заказа и запросов (order_id/trace_id)
- Прокидывать: Shop API ↔ CRM API ↔ RabbitMQ ↔ MES API.
- Логировать в структурированных логах.
- Добавить в сообщения RabbitMQ headers: correlation-id, causation-id, message-id.

I2. Метрики + дашборды + алёрты (продуктовые и технические)
- RabbitMQ:
  - queue depth, publish/consume rate, consumer count, unacked, redelivered.
- MES price calc:
  - длительность, очередь задач, процент ошибок, таймауты.
- Заказы:
  - time-in-status, SLA violations (например, “SUBMITTED → PRICE_CALCULATED”),
  - доля “зависших” > N часов/дней.
- SLO/алёрты: “заказ не дошёл до MES за X минут”, “DLQ > 0”, “lag растёт 15 минут”.

I3. Распределённая трассировка (OpenTelemetry) для Shop/CRM/MES
- Трейсы по HTTP + по обработке сообщений из MQ.
- Это резко сокращает MTTR по “пропал заказ”.

2.2. Надёжная интеграция через RabbitMQ (убрать «пропажи»)
I4. Внедрить transactional outbox для публикации событий (CRM и/или Shop, где рождается событие)
- Суть: запись бизнес-данных + запись события в outbox-таблицу в одной транзакции БД.
- Отдельный publisher читает outbox и публикует в RabbitMQ (с ретраями).
- Устраняет расхождение “в БД записали, в MQ не отправили”.

I5. Внедрить inbox + идемпотентность консьюмеров (MES/CRM)
- Хранить message-id обработанных сообщений.
- Повторная доставка не ломает состояние.
- Обработку делать “атомарно”: inbox record + обновление заказа.

I6. Настроить retry policy и DLQ (dead-letter) на очередях
- “Ядовитые” сообщения не должны блокировать поток.
- Добавить “parking lot” и операционный процесс разборов.

I7. Явно описать контракты событий (event schema/versioning)
- Схемы (JSON Schema/Avro/Proto) + версионирование.
- Контрактные тесты между командами/сервисами.

2.3. Разгрузка и масштабирование расчёта стоимости (главный источник тяжёлых нагрузок)
I8. Асинхронный расчёт стоимости: выделить “Price Calculation” как job queue + worker pool
- Из MES API сделать:
  - принять запрос,
  - создать job (в БД/очереди),
  - вернуть 202 Accepted + job_id,
  - результат отдавать по polling endpoint / webhook callback.
- Воркеры масштабируются независимо от UI/MES API.
- Для очень долгих расчётов — heartbeat/progress.

I9. Кеширование результатов расчёта (по хешу 3D-модели + параметрам)
- Ключ: hash(file) + материал/размер/параметры.
- TTL/инвалидация по изменению алгоритма (versioned key).
- Сильно снижает нагрузку при повторных запросах партнёров и “переоткрытиях” заказов.

I10. Ограничение нагрузки на внешнем API (rate limiting/quotas)
- По API key/клиенту:
  - RPS,
  - параллельные job’ы,
  - дневные лимиты.
- Backpressure: при перегрузе возвращать 429/503 с Retry-After.

I11. Приоритизация B2C vs B2B
- Разные очереди/пулы воркеров.
- Гарантировать, что партнёры не “съедают” весь ресурс.

2.4. Ускорение дашборда MES (критично для операторов)
I12. Оптимизация запросов и индексов в MES DB под сценарий “новые заказы по статусам”
- Индексы:
  - (status, created_at desc) или (status, updated_at desc),
  - частичные индексы по “активным” статусам.
- Перейти на keyset pagination (seek) вместо OFFSET.
- Отдельный endpoint “top-N newest per status”.

I13. Read-model / materialized view / кеш для “дашборда по статусам”
Варианты (выбрать по сложности):
- Вариант A (быстрее внедрить): Redis-кеш “top newest orders by status” + инвалидация по событию статуса.
- Вариант B (надёжнее): отдельная таблица/проекция “order_status_projection” (денормализация) обновляемая по событиям.
- Цель: отдавать дашборд за десятки миллисекунд даже на больших объёмах.

I14. Блокировки/конкуренция “взять заказ в работу”
- Чтобы “кто первый взял — того и заказ” работало корректно и быстро:
  - оптимистическая блокировка / SELECT … FOR UPDATE SKIP LOCKED,
  - явная операция “claim order” атомарно.

2.5. Кеширование в Shop/CRM (дополнительная экономия БД)
I15. Кеш для каталога/справочников/частых чтений (Redis)
- Каталог товаров, элементы конструктора, справочники статусов/ценностей.
- Снижение нагрузки на Shop DB.

I16. CDN/кеширование статики и 3D-ассетов (где применимо)
- Раздача тяжёлых файлов через объектное хранилище + CDN.
- Pre-signed URL для загрузки/скачивания, чтобы API не был “трубой” для файлов.

2.6. Масштабирование и отказоустойчивость инфраструктуры
I17. Горизонтальное масштабирование stateless API (Shop API/CRM API/MES API)
- LB + 2+ инстанса.
- “Zero-downtime deploy” (rolling).

I18. Read replicas для PostgreSQL и разделение read/write
- Дашборды и списки — на чтение.
- Запись статусов/заказов — на primary.

I19. Нагрузочное тестирование и capacity planning (регулярно)
- Сценарии: всплеск партнёров, массовые расчёты, рост заказов.
- Цель: знать пределы и иметь план масштабирования.

2.7. Процессы поставки (чтобы успевать чинить)
I20. Автоматизация регресса (минимум smoke E2E) + ускорение релиза
- Авто smoke на release, контрактные тесты по событиям.
- Убрать “месячные” задержки поставки фиксов.

I21. Канареечные/поэтапные релизы + быстрый rollback
- Особенно важно для изменений MQ/статусов/воркеров.

3) Приоритизация инициатив (с аргументацией)
Критерии:
- (A) Прямо снижает потери заказов/просрочки (самая дорогая проблема для бизнеса).
- (B) Быстро даёт диагностируемость (сокращает MTTR).
- (C) Снимает главные узкие места под рост нагрузки (API + расчёты + дашборды).
- (D) Реалистично для команды за 1–2 спринта/несколько спринтов.

Приоритет P0 (срочно, “остановить кровотечение”)
P0-1: I2 + I3 + I1 (наблюдаемость end-to-end)
- Без этого любые изменения “вслепую”.
- Даст ответ: где именно пропадают/задерживаются заказы (MQ? консьюмер? БД? расчёт?).

P0-2: I6 (DLQ + ретраи) + базовая операционка по очередям
- Немедленно снижает риск блокировок и накопления “ядовитых” сообщений.

P0-3: I5 (идемпотентность консьюмеров)
- В event-driven системах дубликаты неизбежны; без идемпотентности будет либо потеря, либо поломка.

Приоритет P1 (устранение системной причины просрочек)
P1-1: I4 (transactional outbox)
- Убирает классический источник “заказ есть в БД, но не ушёл в MQ”.

P1-2: I8 (асинхронный расчёт + воркеры)
- Изолирует тяжёлую работу от MES API/UI, повышает стабильность, позволяет масштабировать отдельно.

P1-3: I10 + I11 (rate limiting + приоритизация B2C/B2B)
- После открытия API это must-have, иначе партнёры будут деградировать весь контур.

Приоритет P2 (производительность MES и рост)
P2-1: I12 + I13 (индексы/запросы + read-model/кеш дашборда)
- Прямой эффект на скорость работы операторов и на нагрузку БД.

P2-2: I17 + I18 (масштабирование API + read replicas)
- Убирает SPOF и даёт запас по росту.

Приоритет P3 (ускорение поставки и дальнейшая оптимизация)
P3-1: I20 + I21 (автотесты/канарейки/rollback)
- Нужны, чтобы изменения по очередям/статусам не “ломали прод” и быстрее доезжали.

P3-2: I9 (кеш результатов расчёта), I15–I16 (кеширование в Shop/CRM, CDN)
- Оптимизации, которые сильно полезны на масштабе, особенно при повторных запросах.

4) Целевая архитектура через полгода (To-Be, 6 месяцев)
Цель: система выдерживает рост заказов и партнёров, заказы не “теряются”, есть наблюдаемость и управляемые очереди, тяжёлые вычисления изолированы.

4.1. Архитектурные принципы
- Event-driven интеграция с гарантией at-least-once + идемпотентность.
- Асинхронные долгие операции (price calc) через job queue.
- Разделение write-модели и read-моделей (проекции) там, где UI требует быстрых списков/дашбордов.
- Горизонтально масштабируемые stateless API.
- Наблюдаемость по SLO.

4.2. Состав (логически)
- RabbitMQ остаётся, но:
  - настроены DLQ, ретраи, мониторинг,
  - внедрены outbox/inbox,
  - определены схемы событий и версии.
- Price Calculation:
  - отдельный компонент “price-calc workers” (может быть частью MES, но масштабируется отдельно),
  - очередь задач расчёта,
  - API: submit job / get result / webhook.
- MES dashboard:
  - read model (таблица-проекция или Redis) для “новые заказы по статусам”.
- Периметр для внешнего API:
  - API gateway (или аналог) с rate limiting/quotas.
- Observability stack:
  - метрики (Prometheus), дашборды (Grafana), логи (Loki/ELK), трейсы (Jaeger/Tempo), алёртинг.
- HA:
  - 2+ инстанса приложений за LB,
  - read replicas для PostgreSQL (минимум для MES DB при активных дашбордах).

Ожидаемый эффект:
- Снижение “пропавших” заказов (за счёт outbox/inbox, DLQ, мониторинга).
- Контролируемая деградация при всплесках (rate limit, очереди, приоритизация).
- Ускорение MES главной страницы (индексы + проекции).
- Быстрее релизы фиксов (smoke/канарейки/rollback).

5) Если можно сделать только 3 пункта за ближайшие полгода — что выбрать и почему

Выбор 1: Наблюдаемость end-to-end (I1 + I2 + I3)
Почему:
- Сейчас неизвестно, где именно ломается цепочка заказов и почему растут просрочки.
- Это самый быстрый способ сократить MTTR и перестать “гадать”.
- Это база для проверки эффективности всех остальных изменений.

Выбор 2: Надёжная интеграция через MQ (I4 + I5 + I6)
Почему:
- Основная боль бизнеса — заказы “не доходят” и статусы расходятся.
- Outbox/inbox + DLQ/ретраи практически всегда дают кратный эффект по надёжности в распределённых системах.
- Это напрямую бьёт по потерям контрактов и недовольству клиентов.

Выбор 3: Асинхронный расчёт стоимости с воркерами + защита внешнего API (I8 + I10 (+I11 по возможности))
Почему:
- Расчёт — самый тяжёлый и самый масштабируемый узел нагрузки, а также точка, которую усилило открытие API.
- Асинхронность и отдельные воркеры дадут управляемость: очередь, приоритеты, автоскейл.
- Rate limiting не даст партнёрам “положить” MES и ухудшать B2C.

Примечание:
- Оптимизацию MES-дэшборда (I12/I13) я бы поставил следующим (4-м) приоритетом: она очень важна для операторов, но без надёжной интеграции и наблюдаемости мы рискуем ускорить UI, не решив “пропажу заказов”.

6) Черновой план реализации (очень укрупнённо по этапам)
Этап A (1–2 спринта): Observability + RabbitMQ health
- Correlation-id, structured logs
- Метрики RabbitMQ/консьюмеров, алёрты по лагу и DLQ
- Базовые дашборды по time-in-status

Этап B (2–4 спринта): Надёжность событий
- Inbox + идемпотентность на консьюмерах
- DLQ/ретраи/parking lot
- Outbox на продюсере(ах)

Этап C (2–4 спринта): Price calc async + защита API
- Job model + воркеры + API 202/job_id
- Rate limiting/quotas + разные очереди для B2C/B2B

Этап D (параллельно/после): MES dashboard performance
- Индексы + keyset pagination
- Read-model/Redis для “top newest orders by status”
